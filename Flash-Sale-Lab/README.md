# Flash-Sale-Lab — 3일 미니 플래시세일 인프라 실습

> 대규모 트래픽이 몰리는 **플래시세일 시스템을 로컬 스케일로 직접 구축**하며, **시스템 설계 → 구성 → AIOps 자동화 → 부하 테스트**를 팀프로젝트처럼 처음부터 끝까지 해보는 3일 실습.

## 왜 이 실습인가

- **설계를 처음** 해보니까 → 설계 근육을 먼저 만든다 (Day 1 전체가 설계)
- 실전 전에 **설계→검증 한 사이클을 미리 돌려본다**
- 트레이드오프를 **직접 고민하고 결정을 기록**하는 습관을 만든다
- 개발은 **바이브코딩으로 최소**, 인프라/자동화/검증에 집중

## 실습 도메인

**미니 플래시세일**: 한정 수량 상품에 동시 주문이 몰릴 때
- ✅ **재고를 초과 판매하지 않는다** (정합성)
- ✅ **트래픽 폭주를 버틴다** (완충·확장)
- ✅ **무슨 일이 일어나는지 관측된다** (Observability)
- ✅ **운영을 AI가 돕는다** (AIOps: 이상탐지·데일리 리포트)

> 실무의 대규모(수십만 VU·K8s·멀티리전)는 로컬에서 불가능하고 불필요하다. **같은 문제·같은 사고방식을 로컬 스케일로** 재현하는 게 목표. (원칙: 실험·검증은 로컬, 규모가 필요한 것만 클라우드)

## 팀프로젝트처럼 하는 법 (1인 다역)

혼자지만 실제 팀처럼 굴린다:
- **역할 모자 바꿔쓰기** — 지금 나는 "설계자 / 백엔드 / 인프라 / SRE / 발표자" 중 누구인가를 의식
- **매일 데일리 리포트 작성** ([템플릿](templates/DAILY_REPORT.md)) — 어제 한 일 / 오늘 할 일 / 막힌 것 / 결정
- **모든 기술 결정은 결정 로그에** — "왜 이걸 골랐나 / 대안 / 트레이드오프"
- **하루 끝 KPT 회고** 한 줄씩

## 완료 기준 (이 실습을 마쳤다고 말하려면)

- [ ] 재고 정합성이 동시 요청에서 깨지지 않는다 (초과판매 0건)
- [ ] 동기 vs 비동기(큐) **두 버전을 A/B로 비교**한 수치가 있다
- [ ] Grafana에서 RPS·지연·에러율을 **눈으로 본다**
- [ ] 로그/메트릭 기반 **AI 자동화 1개**가 실제로 동작한다
- [ ] 결정 로그 **5건 이상**, 각각 트레이드오프가 적혀 있다
- [ ] 부하 리포트에 **목표 수치 vs 실측**이 있다

## 사전 준비물

- Docker / docker-compose (이미 설치됨)
- k6 (`brew install k6`)
- 선택: kind 또는 minikube (K8s/KEDA까지 도전 시)
- LLM 호출 수단 (AIOps 자동화용 — API 키 또는 로컬 모델)

## 기술 스택 (로컬 실현 가능 버전)

| 영역 | 실무 규모(참고) | 이 실습(로컬) |
|------|----------------|---------------|
| 앱 | Spring Boot/Java 등 | 자유 (Spring/FastAPI/Node — 바이브코딩) |
| 메시징 | Kafka 3-Broker (K8s) | Kafka (docker-compose, 단일→3broker A/B) |
| DB / 캐시 | 관리형 RDB / 관리형 캐시 | MySQL(or PG) / Redis (docker) |
| 오케스트레이션 | K8s + 노드 오토스케일 | docker-compose (도전: kind + KEDA) |
| 관측 | 상용 APM | Prometheus + Grafana + Loki |
| 부하 | 분산 부하도구 | k6 로컬 |
| 자동화 | 룰 기반 알림 | **LLM 이상탐지 + 데일리 리포트** ← 이 실습의 핵심 |
