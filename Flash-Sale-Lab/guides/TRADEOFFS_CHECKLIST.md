## A. 데이터 & 정합성

### A1. 재고 차감을 어디서 지킬 것인가
| 선택지 | 장점 | 단점 |
|--------|------|------|
| DB 트랜잭션 + 락 (SELECT ... FOR UPDATE) | 강한 정합성, 익숙함 | 락 경합 → 처리량 급락, 병목 |
| Redis 원자연산 (DECR/Lua) | 매우 빠름, 경합 적음 | Redis-DB 최종 동기화 필요, 유실 리스크 |
| DB 낙관적 락 (version 컬럼) | 락 없이 충돌 감지 | 충돌 시 재시도 로직 필요 |

❓ 초과판매를 0건으로 막는 게 최우선인가, 처리량이 최우선인가? 재고 소진 후 요청은 얼마나 빨리 쳐내야 하나?

### A2. DB — 관계형 vs 그 외
❓ 주문/재고는 트랜잭션이 필요 → 대부분 RDB. NoSQL이 필요한 이유가 실제로 있나? (없으면 MySQL/PG)

### A3. 캐시(Redis)를 쓸 것인가, 어디에
| 용도 | 쓸 값? |
|------|--------|
| 상품 조회 캐싱 | 읽기 폭주 완화 ✅ / 정합성 주의 |
| 재고 카운터 | 빠른 차감 ✅ / 영속성 주의 |
| 대기열 | 순번 관리 ✅ |
❓ 캐시가 죽으면 어떻게 되나? (캐시는 "있으면 빠른 것"이지 "없으면 안 되는 것"이 되면 위험)

## B. 주문 처리 흐름 (이 실습의 핵심 결정)

### B1. 동기 즉시 처리 vs 비동기 큐(Kafka)
| 선택지 | 장점 | 단점 |
|--------|------|------|
| 동기 (요청→DB 저장→응답) | 단순, 즉시 결과, 구현 빠름 | 폭주 시 DB 직격, 스파이크에 취약 |
| 비동기 (요청→큐→컨슈머 처리) | **폭주 완충**, 확장 쉬움, 장애 격리 | 복잡도↑, 결과 즉시성↓(주문 "접수"와 "확정" 분리) |

❓ 우리 목표 트래픽이 DB가 직접 감당 가능한 수준인가? "주문 접수됨"과 "주문 확정됨"을 분리해도 UX가 괜찮은가?
> **실습 지시**: Day 2에 **동기 먼저** 만들고, Day 3에서 부하로 깨진 뒤 비동기로 전환해 A/B 비교. (문제를 겪고 나서 도입 = 진짜 근거)

### B2. 메시지 브로커 — Kafka vs RabbitMQ vs Redis Stream vs SQS
| 선택지 | 강점 | 이 실습 적합성 |
|--------|------|----------------|
| Kafka | 고처리량, 재처리, 파티션 확장 | 실무 표준, 학습가치 ↑ |
| RabbitMQ | 라우팅 유연, 가벼움 | 순서/재처리 약함 |
| Redis Stream | 이미 Redis 있으면 간단 | 대규모엔 한계 |
| SQS(클라우드) | 관리형, 무운영 | 로컬 실습엔 부적합 |
❓ 재처리·순서 보장·컨슈머 확장이 필요한가? (필요 없으면 Kafka는 과할 수도 — 근거를 남겨라)

### B3. 실패 처리 — 재시도/DLT를 어떻게
❓ 실패한 메시지가 **정상 메시지를 막지 않게** 하려면? (예: 단계적 재시도 → DLT 격리)
- 즉시 재시도 vs 지연 재시도(1s→5s→30s) vs DLT로 격리 후 수동 처리
- ❓ 실패 원인별로 재시도 전략이 달라야 하나? (네트워크 일시 vs DB 다운 vs 데이터 오류)

## C. 확장 & 인프라

### C1. 단일 인스턴스 vs 수평 확장
❓ 하나로 목표를 못 버티면 늘린다. 늘릴 때 **상태(state)를 공유**하는가? (세션·재고 카운터가 인스턴스에 갇히면 안 됨)

### C2. Kafka 단일 broker vs 3-broker
| | 단일 | 3-broker (RF=3) |
|--|------|-----------------|
| 장점 | 단순, 가벼움 | 브로커 1개 죽어도 무손실 |
| 단점 | **SPOF** | 리소스↑, 설정 복잡 |
❓ "장애를 견딘다"가 목표인가? → Day 3에서 **단일 vs 3-broker를 A/B로** 직접 비교(브로커 죽이고 복구시간 측정).

### C3. 오케스트레이션 — docker-compose vs K8s(kind)+KEDA
❓ 실습 목표가 "돌아가게"면 compose로 충분. "오토스케일링을 보여주겠다"면 kind+KEDA 도전.
> 초과 도전은 시간 예산과 상담. **먼저 compose로 완주**하고 여유 있으면 K8s.

### C4. 오토스케일링 트리거 — 무엇을 기준으로
❓ CPU? 큐 lag? RPS? (교훈: 지표 여러 개가 싸우면 thrashing → **단일 신뢰 지표**로 시작)

### D1. 무엇을 볼 것인가 (3대 요소)
- **메트릭**(Prometheus): RPS, 지연 분위수(P50/P95/P99), 에러율, 큐 lag

## E. AIOps 자동화 (우리 차별화)

### E1. AI로 무엇을 자동화할 가치가 있나
| 후보 | 가치 | 난이도 |
|------|------|--------|
| 로그/메트릭 이상 요약 | 장애를 빨리 이해 | 중 |
| 데일리 리포트 (Git+회의+할일 종합) | 협업·아카이브·발표 | 중 |
| 이상탐지 → 알림 | 선제 대응 | 중상 |
| 부하결과 자동 리포트화 | 발표 자동화 | 하 |
❓ "AI를 위한 AI"가 되지 않게: **실제로 사람 일을 줄이는가?** ([의사결정 렌즈](DESIGN_GUIDE.md) 적용)

### E2. LLM 파이프라인 — 룰기반 vs LLM vs Agent
❓ 단순 임계치 알림은 룰로 충분(LLM 불필요). LLM은 **요약·판단·종합**이 필요한 곳에. Agent는 여러 소스를 오케스트레이션할 때.
