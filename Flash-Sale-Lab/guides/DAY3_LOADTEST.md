## 오전 1 — k6 시나리오 + 스모크 테스트

- [ ] `k6/purchase.js`: 세일 시작 → 주문 폭주 시나리오
- [ ] 단계적 부하(ramping): 100 → 500 → 1,000 → 2,000 VU
- [ ] 측정: RPS, P95/P99, 에러율, (비동기면) 큐 lag
- [ ] 먼저 **스모크**(소규모)로 스크립트가 맞는지 확인

```js
// k6/purchase.js 뼈대
import http from 'k6/http';
import { check } from 'k6';
export const options = {
  stages: [
    { duration: '30s', target: 500 },
    { duration: '1m',  target: 1000 },
    { duration: '30s', target: 2000 },
    { duration: '30s', target: 0 },
  ],
  thresholds: { http_req_duration: ['p(99)<300'], http_req_failed: ['rate<0.01'] },
};
export default function () {
  const res = http.post('http://localhost:8080/purchase', JSON.stringify({ productId: 1 }), 
    { headers: { 'Content-Type': 'application/json' } });
  check(res, { 'status ok': (r) => r.status === 200 || r.status === 202 });
}
```

## 오후 2 — 병목 찾기 + 튜닝

**측정 → 가설 → 조치 → 재측정** 사이클. 추측으로 건드리지 마라.

대규모 시스템이 흔히 겪는 병목들 — 만나면 힌트:
- DB "too many connections" → 커넥션 풀 vs 인스턴스 수 관계 (`maxReplicas × pool ≤ DB max_conn`)
- 특정 서비스 OOM → 진짜 원인이 그 서비스인가? (증상이 난 곳과 원인이 다를 수 있다 — 사이드카·프록시 의심)
- 스케일링이 안 먹힘 → 트리거/설정 충돌
